# RF-01 · 신규 기술자산 즉시 등록 설계 — 현재 맥락 → 스토리 카드 → 증분 검색 v1.0

## 1. 목적
과거 아카이브를 다시 탐색하는 비용과 달리, **지금 개발에 참여하는 Chat/Work가 이미 이해한 작업 맥락**을 종료 시점에 자산화한다.
새로운 자료가 들어오지 않는 날에는 인덱싱 작업이 0건이며, 신규 등록이 1건이면 해당 1건만 처리한다.

## 2. 권장 카드 스키마 (v0 후보; 공식 레지스트리 변경 아님)
- story_id: 중복되지 않는 내부 식별자
- session_and_project: 현재 작업번호/모드/관련 프로젝트
- trigger: 이 카드의 생성 이유 (작업완료/사용자 승인/중요 실패 교정 등)
- title, problem, context, attempts, failed_attempts, pivot_reason, chosen_solution, alternatives_not_chosen
- applicability, constraints, risks, limitations, outcome, testing_status
- evidence: [{source_path, section_or_line, sha256_if_already_known, kind, validation_level}]
- user_verbatim: 사용자 발언 원문에 대한 **정확한 부분 인용 또는 별도 원문 참조**, 요약·해석은 별도 필드
- inferred_context: AI 가설/권고, 실측 사실과 구분
- tags, synonyms, hangul_initials, related_story_ids, related_asset_ids
- ingestion_status: DRAFT, EVIDENCE_LINKED, INDEXED_DEV, SEARCH_CONFIRMED, FEEDBACK_CANDIDATE, OFFICIAL_APPROVAL_PENDING, OFFICIAL_APPROVED
- version, created_at, provenance, review_status

## 3. 필요한 사건만 캡처
개발 중 모든 메시지를 재분석하지 않는다. 중요한 (1) 실패/원인 발견 (2) 설계 방향 전환 (3) 사용자 승인 (4) 실제 시험 PASS/FAIL이 발생할 때 짧은 체크포인트를 남긴다.
작업 종료 시 체크포인트와 **현재 AI의 맥락**을 활용해 한 번만 후보 카드를 만든다. 사용자가 원문 발언을 제공했다면 원문을 삭제하지 않고 참조한다.

## 4. 신규 등록 절차
1. 작업 종료 신호(사용자 요청 또는 Work 종료 절차) → 등록 후보 생성.
2. 현재 맥락 + 이미 보유한 증거 위치/검증 상태로 카드 초안 구성. 새로운 전체 원문 읽기 강제 금지.
3. 원본 경로, 실제 수행한 시험과 변경 금지 경계만 최소 확인. 없는 증거를 상상으로 보강하지 않는다.
4. 사용자 승인이 필요한 운영 변경·대장 반영을 자동 수행하지 않는다.
5. 격리 대상 디렉터리에 카드 JSON/스토리 MD 저장.
6. SQLite 파생 검색 DB에 **신규 카드만** 증분 등록. 기존 등록 전체 재인덱싱 금지.
7. 현재 작업자가 아닌 새 질의/새 프로세스로 검색 → 지정 스토리의 경로·근거 섹션 확인.
8. 처음 실패하면 누락한 별칭/문제/해결 설명을 보강하고 카드 버전을 추가하여 비교. 기존 원문이나 증거 자체를 수정하지 않는다.
9. 격리 시험의 결과를 Chat에 인계하고, 공식 등록은 별도 승인 절차로 결정.

## 5. 점진적 아카이브 복원
- 백서에서 1차 스토리 후보를 만들고 필요한 자료만 정밀 카드화.
- 신규 카드에는 관련된 **미색인 과거 스토리 ID**를 연결할 수 있다. 필요해졌을 때 그 스토리만 복원·심화한다.
- 과거 스토리 원문의 승인 상태/실제 운영 구현 상태를 먼저 확인한다. 백서의 출판/교열 여부와 검색 참조 가능 여부는 다르다.
- 후보 대장 자체는 얕은 탐색용 데이터다. 모든 과거 파일의 해시·본문을 미리 다시 검사하는 작업이 아니다.

## 6. 가장 중요한 계측
A. 단계별 **사람/AI 작성 경과시간**: 사건 정리, 자동 카드 초안, 원본 연결, 검토, 색인 등록, 독립 검색, 결과 보고.
B. 카드 생성 시 실제 입력 토큰/출력 토큰/모델 호출(측정 불가하면 미측정), 재입력한 원본문자 수.
C. 카드에 있는 문제·실패·해결 원칙의 근거 충실도, 누락·허구·출처 혼동 개수.
D. 새로운 AI/새 검색 프로세스가 해당 스토리를 다른 표현으로 찾아내는 비율.
E. 검색 p95는 부차 지표, **같은 실패를 피하고 신규 작업에 실질 적용한 검증**이 최종 지표.

## 7. 통제
- 사용자가 최근 지적한 19분의 총 작업시간이 다시 설명되지 않는 문제가 생기지 않도록, 작업 단계마다 간단한 시각/시간 기록이 중요하다.
- 이미 동결한 원본을 반복 전수 검증하지 않는다. 최초 발견·새 등록·충돌/오류 검증으로 충분하다.
- 예상 작업시간을 임의로 약속하지 말고 **실제 계측된 시간만 기록**한다.
- 정보 누출 위험이 있는 실제 비밀키와 개인정보는 일반 검색 카드에 싣지 않는다.
- 현재 Work에서 자동등록을 검증할 수는 있어도, 별도 승인 없는 무인 백그라운드 시스템을 만든 것으로 보고하지 않는다.

5. 과거 스토리 후보는 02_ARCHIVE_STORY_CANDIDATES.csv를 시작점으로 삼되, 필요한 2~3개만 실제 코드/문서와 깊게 연결한다.

**결정: 신규는 즉시 등록, 과거는 스토리 목록 보유 후 필요 시 복원. 인덱싱 품질에 자원을 집중하고 검색은 가볍게.**
