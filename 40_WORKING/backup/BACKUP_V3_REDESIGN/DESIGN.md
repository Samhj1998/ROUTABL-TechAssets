# 기술자산 백업 v3 설계안 v0.2 (2026-11-14 08:10, 제안 — 승인 전)

이전 판(v0.1, 커밋 381ffb9)은 기존 구조를 단순화하는 안이었다. v0.2는 사용자가 제시한 두 전제 위에서 처음부터 다시 설계한다.

## 전제 (사용자, 11-14)
1. **기술자산은 비밀이 아니라 공개 자료다.** 비밀 취급을 전제로 한 암호화·SHA 고정·승인 파일·다단 감독이 복잡성의 근원.
2. **기술자산의 가치는 다음 프로젝트에서의 활용도다.** 자산 자체의 완벽함이 목표가 아니다. 더 나은 기술이 나오면 교체하고 그것을 다시 자산으로 삼는다.

## 결론: 백업에 '알고리즘'은 거의 필요 없다
- 텍스트 자산은 이미 git으로 관리된다. git은 모든 판본의 이력과 내용 해시를 스스로 보관·검증한다.
- 따라서 백업 = **git 저장소를 다른 곳에 복제(push)하는 것**. 복원 = clone. 검증 = `git fsck` + 커밋 해시 비교.

## 구조 (3층)
| 층 | 대상 | 백업 방법 | 빈도 |
|---|---|---|---|
| 1. 지식 (공개) | git 추적 텍스트 576개, .git 약 6MB: 원칙·설계·코드·테스트·감사 기록 | `git push` → **GitHub 공개 저장소** + **NAS 저장소** | 커밋할 때마다 자동(post-commit) + 매일 1회 보정 |
| 2. 큰 원본 | `20_ORIGINALS` 약 7.5GB, `80_RUNTIME` 약 0.2GB | `rsync`로 NAS 단방향 복사(지우지 않음). 판본 보관은 Synology 스냅샷 기능에 맡김 | 매일 1회 |
| 3. 비공개 | 고객 정보(업체명·주소·캡처 사진), 개인 대화 내보내기, 키·비밀번호 | 공개 저장소에서 **제외**(.gitignore). NAS에만 보관 | 2층과 함께 |

- 3층은 "기술 비밀"이라서가 아니라 **남의 정보·개인정보·계정 보안** 때문에 제외한다. 예: 현재 git에 `40_WORKING/customer/.../samples/F1_kakao_에이치엘텍스.jpg` 등 실제 업체 캡처가 추적 중 → 공개 전 제외 필요.
- 키·비밀번호는 원래 어디에도 백업 대상이 아님(각 서비스에서 재발급).

## 실행 구성
- 스크립트 1개(`backup_v3.sh`, 30줄 안팎): ① 1층 push(원격 2곳) ② 2층 rsync ③ 결과 1줄을 `runs.log`에 추가 ④ 실패면 macOS 알림.
- 예약 1개(launchd, 매일 1회). 실패해도 다음 날 다시 실행되며 git push·rsync는 반복해도 안전(멱등).
- 실행 기록이 2일 이상 끊기면 스크립트가 다음 실행 때 알림.
- 승인 파일·SHA 고정·감독자·관리자 앱 없음.

## 기대 효과 (전제 2 기준)
- GitHub 공개 저장소 = **어느 AI·어느 기기·새 프로젝트에서도 바로 읽는 자산**. Claude·ChatGPT가 Mac 로컬 검색(8772)에 못 닿는 문제도 같이 해결.
- 복원 시험이 `git clone` 한 줄로 끝남 → 매주 자동 시험 가능.

## 공개 전 1회 작업 (승인 필요)
1. 3층 대상 목록 확정 → .gitignore 보강.
2. 과거 이력까지 점검(비밀값·고객 정보 스캔). 이력이 깨끗하지 않으면 **현재 상태로 새 이력 시작**(기존 이력은 NAS 저장소에 그대로 보존).
3. GitHub 공개 저장소 생성(이름 결정).
