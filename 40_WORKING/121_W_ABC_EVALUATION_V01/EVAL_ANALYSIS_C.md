## 1. 병목 (근거 있음) vs 가설 (실측 필요)

**패킷에 근거가 있는 병목**
- **B1. 문서 질의가 전부 SCAN** (M02): 질의어를 별칭으로 확장한 뒤, 용어마다 `path/title/tags/content` 네 열에 리터럴 포함 조건을 OR로 겁니다(M01). 비용은 대략 `행 수 × 용어 수 × 4열 × 문자열 길이`이고, 가장 긴 `content`가 지배적일 것으로 봅니다.
- **B2. 있는 FTS5 trigram `ft`를 쓰지 않음**: MATCH 대조만 VIRTUAL TABLE INDEX를 탄다고 기록돼 있고, 실제 질의는 LIKE로 SCAN합니다. 또 `ft`에는 **`title` 열이 없습니다**(`ft(path,tags,content)`). 그런데 hangul_infix 6건(예: `정색인보` ⊂ 제목 `수정색인보정`)은 제목 일치에 의존합니다.
- **B3. 범위 필터가 Python 단계에 있음**: `nas`·`main` 질의도 전 범위 행을 fetch한 뒤 버립니다. R08은 1776건, R04는 574건입니다.
- **B4. 그룹화를 먼저 하고 페이지를 자름**(M03): 일치 전체를 Python으로 가져와 점수 매기고 묶어야 합니다. 페이지 계약을 바꾸지 않는 한 SQL에서 LIMIT를 걸 수 없습니다.
- **B5. manual은 별도 Python 문자열 매칭**이고 계획은 SCAN입니다.

**실측이 필요한 가설**
- H1: 지연의 대부분은 SQLite 단계, 특히 `content` LIKE입니다. 넓은 질의(R04/R08형)에서는 B4의 Python 후처리가 주된 비용일 수 있습니다.
- H2: manual 테이블은 작아서 B5의 영향은 작습니다.
- H3: 운영에서는 2글자 한글 질의가 흔할 수 있습니다. trigram은 3글자 미만에서 쓸 수 없으므로, 그 비율만큼 개선 폭이 줄어듭니다.
- H4: A는 jamo_intent 6건(Q05/10/15/30/35/40)에서 0건을 반환합니다. 현행 규칙에 초성 전처리가 없기 때문입니다(M03). 표본에서 초성 질의는 **제목이 아니라 본문 첫 어절**과 맞았습니다. 예: `ㄱㅈㄱㅊ` ↔ `결정관측원리`, `ㅇㄹㅍㅂ` ↔ `연륜표본보존`, `ㅂㅂㅅ` ↔ `빛분산관측법`.

## 2. 우선 구현안: FTS5 trigram으로 후보를 좁히고 v1.5 판정으로 다시 확인

일치 판정, 점수, 정렬, 그룹화는 v1.5 코드를 그대로 씁니다. 바뀌는 것은 **어떤 행을 Python으로 가져오느냐**뿐입니다. 후보 집합이 v1.5 일치 집합을 빠짐없이 포함(⊇)하기만 하면, 결과는 구조적으로 v1.5와 같습니다.

```python
def query_docs(conn, raw, scope):
    terms = expand_aliases(normalize(raw))          # v1.5 그대로
    if FTS_OFF or any(len(t) < 3 for t in terms) or not ft_healthy:
        return query_docs_v15(conn, raw, scope)     # 짧은 질의·이상 시 원 경로
    q = " OR ".join('"' + t.replace('"', '""') + '"' for t in terms)
    cand = conn.execute("""
        SELECT d.* FROM docs d
         WHERE d.path IN (SELECT path FROM ft WHERE ft MATCH :q)
        UNION
        SELECT d.* FROM docs d WHERE <v1.5와 동일한 title LIKE OR 식>
    """, ...).fetchall()
    rows = [r for r in cand if matches_v15(r, terms)]  # 원 판정으로 재확인
    return group_page_v15(score_v15(rows), scope)      # 범위·점수·그룹·페이지 불변
```

- **선행 확인 3가지**(`sqlite_schema`):
  - `ft`가 일반·external·contentless 중 무엇인지. contentless면 `path`를 꺼낼 수 없으니 rowid로 조인해야 합니다.
  - `path`가 UNINDEXED인지. 그렇다면 path LIKE 분기를 따로 둬야 합니다.
  - `detail=` 옵션. none이어도 후보가 늘 뿐이라 ⊇는 유지됩니다.
- **⊇가 성립하는 근거**: trigram `case_sensitive=0`은 ASCII를 포함한 유니코드 대소문자를 접습니다. LIKE는 ASCII만 접으므로 trigram 쪽이 더 넓습니다. 따옴표로 묶은 phrase는 부분 문자열 조건과 같습니다. 3글자 미만 질의는 원 경로로 보냅니다.
- **예상 비용(예측)**:
  - 저장 공간 +0. `ft`가 이미 있기 때문입니다.
  - 색인 시간 +0. `ft`가 이미 동기화되어 있다는 전제입니다.
  - 제목 분기는 여전히 docs SCAN이지만 긴 `content`를 비교하지 않습니다.
  - 측정해서 제목 스캔이 지배적이면, 하위 단계로 커버링 인덱스 `docs(title, path)`를 추가합니다. 추가 공간은 대략 `Σ(len(title)+len(path))×1.3`(가설)입니다.
  - p95는 선택적 질의(정확 ID, 본문 6글자, 제목 4글자)에서 크게 줄어들 것으로 예측합니다. 넓은 질의(R04/R08형)는 B4가 남아 개선이 작을 것으로 예측합니다. 모두 미측정입니다.

## 3. 호환성 및 회귀 위험

| 항목 | 영향 | 위험 / 대응 |
|---|---|---|
| 짧은 검색어(2자) | v1.5 경로로 보냄 | 결과 동일, 속도 이득 없음(H3) |
| 한글 부분 일치 | trigram은 음절 단위라 4자 infix 가능. 제목은 별도 분기 | macOS NFD 경로는 v1.5 LIKE와 똑같이 불일치하므로 변화 없음 |
| 초성 | **변화 없음** (A와 같이 0건으로 예상) | 기능 추가는 2단계로 분리하고 별도 승인. 회귀 문자열이 비공개라 반환 수가 바뀔 수 있음 |
| 별칭 | 확장 후 용어마다 OR phrase. 0.65 가중치는 Python에 그대로 | 확장어 중 하나라도 3자 미만이면 전체를 v1.5로 |
| 본문 | `ft.content`에서 후보 추출 | **`ft`가 docs와 어긋나면 누락 발생**. `integrity-check`·행 수·표본 대조를 통과 못 하면 v1.5로 |
| 정렬 | v1.5 점수 + 경로 오름차순 그대로 | UNION으로 순서가 사라지지만 Python에서 다시 정렬하므로 영향 없음 |
| 중복 | SHA-64 묶음 그대로. 표본상 `SIM-00x.md`와 `archive/…-copy.md`가 같은 SHA로 1그룹, `legacy/…-old.md`는 다른 SHA | 대표 경로는 같은 점수에서 경로 오름차순(`S` < `a`)이라 top_path와 맞음 |
| 최신판·검증 | 상태(old = `PDF_TEXT_NOT_EXTRACTED`)와 provenance 보정을 그대로 씀 | 표본에 `version` 필드가 없음. `expected_version: v2`를 어디서 대조하는지 미확인 |

## 4. 평가 계획 (공통 규격 기준)

1. **동등성 게이트**(제일 먼저): 같은 fixture에서 v1.5와 새 구현의 일치 행 집합이 같은지 확인합니다. 대상은 다음과 같습니다.
   - 회귀 9건(평가자 로컬 실행)
   - dev 30건
   - 코퍼스에서 무작위로 뽑은 3~10자 부분 문자열 퍼징
   
   비교 항목은 반환 순서·점수·페이지·중복 개수와 위치·검증 상태입니다.
2. **정확도**: Recall/Precision/MRR/nDCG@10을 macro로 계산합니다. **A 대비 Δ=0이 기대값**입니다(예측).
   - 관련 그룹이 질의당 2개라 P@10 상한은 0.2입니다.
   - ideal DCG는 7 + 1/log₂3 ≈ 7.63입니다.
   - jamo 6건이 0점이면 A의 macro Recall 상한은 약 0.8입니다(가설).
3. **p95**:
   - 유형별(exact_id / hangul_infix / jamo / alias / body)과 회귀형별로 따로 냅니다.
   - 30회 이상 반복, 순서 회전, nearest-rank로 계산합니다.
   - 새 프로세스 첫 호출 / 새 연결 / 재사용 연결을 구분합니다.
   - SQL 준비·fetch, Python 후처리, 직렬화, HTTP를 나눠 기록합니다.
   - 3자 미만 fallback 비율도 함께 보고합니다.
4. **색인 시간**:
   - `ft`를 그대로 쓰면 v1.5 대비 변화 없음을 확인만 합니다.
   - title 인덱스를 추가하면 full / 1건 / 배치 / 무변경 / 삭제·이름 변경으로 나눠 SQL 쓰기와 검증·교체 시간을 잽니다.
5. **저장 공간**: 객체별 bytes를 기록합니다. `dbstat`을 쓰고, 없으면 `sqlite3_analyzer`를 씁니다.

**채택 조건**(제안값이며 최종 목표치는 Chat에서 확정)
- 회귀 9/9 완전 일치
- 동등성 게이트·퍼징에서 불일치 0건
- 어떤 정확도 지표도 하락 없음
- 선택적 질의 유형의 재사용 연결 p95가 30% 이상 개선
- 넓은 질의 유형 p95 악화가 10% 이하
- 저장 공간 증가가 DB 대비 5% 이하

**중단 조건**
- 회귀 불일치가 하나라도 나옴
- ⊇ 위반 사례 발견
- `ft` 동기화를 보장할 수 없음
- fallback 비율이 높아 전체 p95 개선이 기준에 못 미침

## 5. 구현 범위와 불확실성

**구현 범위**
- `query_docs`에 후보 단계를 추가하고 기능 플래그와 `ft` 상태 확인을 붙입니다.
- manual(B5), 범위 필터(B3), 그룹·페이지(B4)는 손대지 않습니다.
- 초성 색인(본문·제목에서 초성 문자열을 파생해 trigram으로 색인), SQL 단계 범위 필터, 2자 질의용 bigram 보조 색인은 **다음 후보**로 남깁니다. 모두 정확도나 계약이 바뀌므로 별도 승인이 필요합니다.

**불확실성**
- `ft`의 스키마·동기화 방식·`path` 색인 여부
- 별칭 설정 내용
- 운영 질의 길이 분포
- `version`·provenance 필드의 위치
- 코퍼스 81행 이후 내용
