# 검색 v1.5 구조와 병목

- 서비스 소스 24~60, 168~247행에서 운영 SQLite 연결, 별칭, 범위, 검색 경로 확인. 입력 2~80자. 지정 별칭 키 10개를 확장한다. 범위 all/main/variants/nas.
- 문서 후보는 path/title/tags/content에 대해 용어별 리터럴 포함 조건을 OR로 구성한다. 파일명은 path에서 파생되어 Python 순위에 반영된다. 본문은 후보 생성에는 쓰이지만 Python 점수의 직접 보너스 항목에는 없다. manual은 모든 행의 필드 연결 문자열을 Python casefold로 비교하므로 ID, 경로, 태그, 설명 등을 통해 매치 가능하다.
- 한글 부분 문자열 매치는 SQLite LIKE의 문자 일치를 이용한다. 확인한 쿼리에는 초성 변환이나 한글 정규화 단계가 없다. 실제 운용 별칭 목록 및 원본 파일 내용은 산출물에 포함하지 않았다.
- Python 108~166, 168~247행에서 파일명·제목 exact/prefix/infix, 경로·태그, 범주, status, 테스트 경로 및 일부 버전 문자열 보정을 적용한다. 용어 가중치는 원문 1.0, 별칭 0.65. 점수 내림차순 및 path 오름차순 후 SHA-256 그룹화. 해시 길이가 64가 아니면 path 기준. 페이지 결과에 중복 위치를 최대 25개 포함한다.
- 원본 경로와 SHA가 동시에 맞는 crosswalk에 가점을 준다. 로드 결과 매핑 2개. GitHub/NAS 검증 상태는 crosswalk 기반 증거이며 일반 상태 OK와 다른 필드다. 날짜·버전 비교를 통한 일반적인 최신판 강제 우선 로직은 확인되지 않았다. v0.4 이름 가점과 provenance 가점이 존재한다.
- v1.5는 v1.4의 인덱스 관리 및 HTTP 틀을 연결하고 v1.4 refresh_worker는 v1.3 scanner.build를 새 후보에 수행한다. v1.3은 이전 DB를 기준으로 복사·순회하고 기존 digest를 조회하며 v1.1 add를 사용한다. v1.1 add의 동일 size/mtime 분기는 scan 표시만 갱신하고 변경행은 docs를 upsert한 뒤 기존 FTS rowid를 지우고 다시 삽입한다. 운영 refresh는 후보 검증·백업·교체 비용을 수반한다. 운영 refresh 경로는 정적 확인만 수행했다.
- 질의 함수는 매 요청 새 SQLite 연결을 연다. 상주 HTTP 프로세스의 상태 및 OS 페이지 캐시는 별개다. 애플리케이션 결과 캐시는 조사한 함수에서 발견되지 않았다. 개별 파일을 질의 때 다시 여는 경로는 확인되지 않았다.
- 계측상 SQLite 조회·행 읽기 평균 115.70ms(전체의 91.2%). SQL 시간이 순수 디스크 I/O인지는 이번 실험으로 분해되지 않는다. 후보 1,776건 NAS 사례 R08에서는 Python과 나머지 평균 59.26ms. 따라서 후보 탐색과 다건 후처리를 구분해 시험할 근거가 있다.
