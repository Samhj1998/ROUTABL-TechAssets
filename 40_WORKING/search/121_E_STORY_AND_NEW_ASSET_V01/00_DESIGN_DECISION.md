- 확정 시점: 2026-11-08, 121 Chat
- 설계 승인: 사용자가 전체 연구 과정을 첫 번째 대표 스토리로 보존하고, 과거 아카이브와 신규 기술자산의 두 갈래를 집중 검증하도록 지시함.
- 작업 단계: **설계/대표 스토리 초안 및 기초 후보 대장 작성 PASS**, 실제 자동 신규등록·운영 연동은 **NOT_TESTED**.
- 상태: 공식 자산 대장 변경 전의 **격리 작업 후보**. 동결 원본·운영 v1.5/Firebase는 변경하지 않음.

## 핵심 판단
**기술자산의 발견 단위는 '스토리/문제해결 경험'이고, 원본 보존 단위는 '파일/원문/증거'다.**

단순 파일명을 찾아내는 것이 아니라 문제 발생 → 시행착오/실패 → 판단·전환 → 해결 원칙 → 검증 → 다른 작업 재사용으로 이어지는 경험을 인덱싱한다.
한 스토리가 여러 문서/코드/로그를 가리키거나 한 백서가 여러 스토리를 포함할 수 있으므로 다대다 관계를 허용한다.
파일명·경로·태그·초성 등은 스토리 발견을 돕는 검색 키일 뿐, 실제 근거를 대신하지 않는다.

## 두 갈래 정책
### A. 과거 아카이브: 얕은 목록 → 필요 시 깊은 복원
- 백서 97-1은 **기술 경험을 빠르게 찾는 내러티브 지도**다. 백서의 장/절/근거 약호를 분석해 스토리 후보를 우선 목록화한다.
- 기존 파일/레지스트리 경로를 연결하되 목록화 작업 때문에 역사적 문서를 전수 재분석하지 않는다.
- 후보 상태를 DISCOVERED(스토리만 발견), SOURCE_LINK_PENDING(연결 근거 미확인), SOURCE_LINKED(근거 경로 있음), DEEP_INDEXED(정밀 인덱스 완료), REUSED_VERIFIED(실제 재사용 실증)로 분리한다.
- 필요할 때 높은 가치의 스토리 하나부터 관련 원본·코드·시험만 추가 조사한다. 스토리·관련파일의 다대다 연결을 사용한다.

### B. 신규 기술자산: 작업 맥락이 살아 있을 때 생성
- 현재 Chat/Work가 문제·실패·대안·승인·구현·검증을 이미 이해하고 있을 때 종료 후보 카드를 생성한다.
- 사건 발생 시 짧은 체크포인트(문제, 실패, 전환, 테스트 증거)를 남길 수 있으나 모든 메시지에서 반복 작업하지 않는다.
- 종료 시 AI가 카드 초안 작성 → 소스/검증 경로 최소 확인 → 신규 원본 및 경험 카드 사본 등록 → 신규분만 SQLite 색인 추가 → 새 질의로 찾아보기.
- 자동화 단계에서는 안전한 명시적 트리거(Work 단계 종료·사용자 요청)가 필요하다. **현재 실제 자동 등록 서비스는 미구현**이므로 자동으로 등록되고 있다고 주장하지 않는다.
- 출처 원문과 AI 요약을 분리한다. 발언 원문과 가공된 스토리 카드의 의미 차이를 나중에 재검토할 수 있도록 한다.
- 출처가 없는 예쁘게 보이는 '회고록'은 근거 수준을 높게 평가하지 않는다.

## 보존·검색·검증 경계
- 일반 기술자료는 재사용 자료. 비밀키/토큰 등 실제 인증 정보와 고객 개인정보만 합리적으로 차단.
- 운영 A(v1.5), 공식 대장, Firebase, GitHub 운영 브랜치, 기술자산 원본, 동결 B/C/V01/V02는 불변.
- 검색 자체는 파일 후보 5~6개 + 관련 스토리 위치 반환. 20개 확대 및 후보 부적합 전환을 유지.
- 속도보다 **스토리의 사실성·검색 발견율·새 개발에서 시행착오 회피**가 우선.
- 저가 AI/SSD/RAM 캐시는 활용 수단이다. 근거 없는 맥락이나 부실한 색인은 빠른 쿼리로 고칠 수 없다.
