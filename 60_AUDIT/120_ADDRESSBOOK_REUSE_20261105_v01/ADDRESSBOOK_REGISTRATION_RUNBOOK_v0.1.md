# ROUTABL 사진 기반 주소록 등록 — 표준 실행 절차 v0.1

대상: 새로운 Chat·Work 세션에서 고객정보 사진과 "기술자산 참고해서 등록해줘" 요청이 들어온 경우.
성격: 재사용용 런북. 이 문서 자체가 권한 부여·자동 프로그램 실행·DB 스키마 변경을 수행하지 않는다.
핵심 원칙: 사용자의 완료 기준은 실제 저장 결과이며 사진 추출·GPS 확인은 중간 단계다.

## 1. 시작 시 기술자산 찾기
1. 120번 레지스트리에서 TA-CASE-20261102-01 및 ROUTABL-ADDR-REUSE-20261105-01을 먼저 검색.
2. Mac Studio 원본 cloud_access.py 위치와 SHA-256 확인. 기존 인증 로직 사용, 토큰·관리자 파일은 출력·복사·외부 공유 금지.
3. 프로젝트 routivel-prod 및 customers 컬렉션을 읽기 전용으로 확인. 앱 전환 시 구 Firebase 프로젝트와 혼동 금지.
4. 기존 연결 경로가 실패했는지 확인하기 전에는 Firebase 신규 연결 자체를 유일한 해결책으로 제시하지 않음.

## 2. 사진과 DB 대조
5. 사진에서 상호명·지번·도로명·연락처·비고를 추출. 불명확하거나 없는 필드는 추측하지 않음.
6. 지도 검색으로 지번·도로명·좌표 일치 여부 대조. 상호명과 위치를 각각 확인.
7. 기존 customers에서 이름·주소·전화번호로 중복 검색. 같은 건물의 다른 업체와 같은 업체의 중복 문서를 구분.
8. 기존 업체 문서가 있거나 충돌하면 자동 수정·덮어쓰기 금지. 대상과 기존 값의 차이를 먼저 정리.

## 3. 실제 등록 (사용자가 승인한 신규 등록 범위 내)
9. 기존 cloud_access.py의 유효한 인증·Firestore 접근 경로를 재사용. 원본 스크립트는 임의 수정하지 않음.
10. 신규만 생성하며 Firestore commit에 currentDocument exists:false 조건 적용. 충돌 시 기존 고객 보존.
11. 한글 문서 ID를 URL 경로로 전달할 경우 반드시 URL 인코딩. UnicodeEncodeError는 API 문법·경로 오류이며 권한 오류와 구별.
12. 필드 명칭, UID 분리, 서버 타임스탬프, 기존 customerDirectoryChanges 동기화 관례 준수. 새로운 스키마 임의 신설 금지.

## 4. 완료 검증
13. 생성한 customers 문서를 서버에서 다시 읽어 업체명·주소·좌표·연락처 등 요청 항목을 비교.
14. customerDirectoryChanges 저널의 동일 고객 반영과 updateTime·데이터 일치 대조.
15. 업체별로 "Firestore 저장 / 서버 재조회 / 변경 저널"을 따로 보고. 실제 안드로이드 앱 표시·새로고침은 별도 실기기 검증 결과가 있을 때만 완료라고 표기.
16. 부분 실패 시 이미 성공한 고객은 반복 쓰지 않고 실패 건만 안전하게 재시험.

## 5. 막혔을 때 경로 탐색
- 이미지 정보 부족: 사진 확인 및 지번·도로명·상호의 여러 출처 대조.
- 원격 도구의 특정 명령 차단: 그 명령의 제한 범위를 파악하고 지원되는 다른 허용 호출 방식 검토; 보안 정책 우회 금지.
- 401/403: 로그인·권한·프로젝트 경계 확인. 권한 상승이나 다른 계정 무단 사용 금지.
- UnicodeEncodeError: 요청 경로 인코딩 및 API 요청 구조 수정 후 동일 단계 재시험.
- ALREADY_EXISTS·409·FAILED_PRECONDITION: 기존 문서 확인 후 create 중지, 수정 필요 여부는 별도 검토.
- 응답 시간 초과: 먼저 서버에서 문서 존재·updateTime 확인하고 중복 저장 방지.
- 안전한 승인 경로가 정말 없다면 완료를 가장하지 않고 오류·시도 경로·허용된 대안·사용자가 필요한 조치를 구체적으로 보고.

## 6. 고객에게 보고할 최종 결과
- 입력 사진 n장, 후보 n건, 신규 저장 n건, 기존 발견 n건, 미완료 n건.
- 업체별 상태: 저장/재조회/변경 저널/단말 반영(미검증 가능).
- 기존 데이터 변경 여부와 저장 증거, 실패가 있으면 오류와 대안.
- 성공 실행의 식별자와 개인정보 제외 영수증을 후속 기술자산에 추가.

주의: 이 절차는 2026-11-05 두 건 성공 경험을 문서화한 v0.1 제안이며, 모든 시스템 및 상황에서 자동 실행 가능한 기능으로 구현되었다는 뜻은 아니다.
