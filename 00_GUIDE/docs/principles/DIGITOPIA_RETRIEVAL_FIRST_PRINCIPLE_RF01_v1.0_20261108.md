# RF-01 · Digitopia 기술자산 검색·복원·재활용 최상위 설계 철학 v1.0

- **제정:** 2026-11-08 KST
- **출처 및 승인:** 121 Chat 사용자 직접 지시 — “최상위 설계 철학으로 등록하고, 철학에 맞게 다음 진행해줘.”
- **분류:** Digitopia 기술자산 수집·색인·검색·활용·환류의 최상위 목적·의사결정 원칙
- **효력:** 새 설계·평가·인계의 상위 판단 기준. 기존 운영 프로그램, DB, 공식 자산대장 및 동결 증거를 이 문서 등록만으로 변경하지 않는다.
- **관리 ID:** RF-01
- **상태:** 사용자 승인 원칙의 신규 문서 등록; 실제 검색엔진 구현·성능 개선은 별도 검증 대상

## 1. 핵심 철학

> **기술자산은 과거의 고민과 노력을 반복하지 않도록, 필요한 경험과 기술을 신속히 찾아 복원하고 새로운 작업에 재활용하기 위한 자원이다.**
>
> **원본은 보존하고, 필요한 자료는 빠르게 찾으며, 새 작업은 사본에서 추출·병합·재생성한다.**

- 기술자산은 기본적으로 **비밀자료가 아닌 참고자료**다. 검색·이해·재활용을 우선한다.
- 기술자산은 만능 답변 창고가 아니다. 원래 자료가 없거나 검색에 실패했거나 현재 과제에 맞지 않으면 신속히 인터넷·외부 자료·다른 기술로 이동한다.
- 새 결과가 오늘 등록되면 내일은 과거 자산이다. 역사적 원본의 수정은 극히 드물며, 새 작업·새 검증 결과는 원본을 덮어쓰기보다 **새 사본·새 자산으로 추가**한다.
- 목표는 검색 DB의 완전무결성 과시가 아니라 **과거 기술을 새 작업에 적용하기까지 걸리는 시간과 비용의 최소화**다.
- 운영 철학: **“생각은 원대하게, 실행은 디테일하게.”** RF-01은 CW-01(Chat↔Work), TI-01(보존/복원), VI-01(버전 독립성)과 공존한다.

## 2. 기준 업무 흐름

1. **등록·환류(Input):** 원본 또는 새 기술자산이 들어올 때 제목·프로젝트·날짜·태그·초성·별칭·본문 위치를 추출하고 필요한 색인을 생성한다. 등록 결과와 원본 연결을 확인한다.
2. **평소 보존:** SSD 원본은 읽기 위주로 유지한다. 색인은 재구축 가능한 파생 데이터다. 수시 검색마다 전체 원본/FTS의 전수 정합성 검사를 수행하지 않는다.
3. **즉시 발견(Retrieve):** 예시로 10,000개 파일 중 관련 5~6개를 빠르게 우선 선정한다. 태그·제목·프로젝트·초성·별칭의 가벼운 색인을 우선 활용하고 필요할 때만 FTS5 본문 검색을 사용한다. 로컬 후보 추출 자체에는 AI 토큰을 쓰지 않는다.
4. **부분 추출(Extract):** 선정된 파일 중 현재 목적과 관련된 단락·코드·의사결정·실패 원인·검증 증거만 찾는다. 무조건 파일 전체를 AI에 전달하지 않는다.
5. **복원·병합·적용(Reuse):** AI가 소수의 근거를 현재 작업에 맞게 병합·재구성한다. 원본은 변경하지 않고 새 작업 공간의 사본/산출물로 생성한다.
6. **검증·환류(Feedback):** 새 작업에서 실제 검증된 개선 결과는 신규 자산으로 등록하고 원본·참조 관계 및 증거를 남긴다. 검색이 부족하면 추가 후보·외부 검색으로 전환한다.

## 3. 자원 소비와 검색 정책

- **읽기 최적화 우선:** 검색 요청마다 FTS 무결성 검사, DB 전체 행·본문 대조, 메모리 DB 전체 복사, 파일 전수 해시 계산을 기본 경로에 넣지 않는다.
- **쓰기/갱신 시 검증:** 파일 최초 등록·수정·인덱스 재구축·세대 교체 시점에 필요한 검사를 수행한다. 가능한 한 변경분만 갱신한다.
- **검색 시 가벼운 상태 확인:** 올바른 색인 세대와 읽기 연결을 저비용으로 확인하고, 문제 발생 시 기존 A 검색/인덱스 재생성/외부 검색으로 빠르게 전환한다. 검색을 막는 장시간 전수 검사보다 유효한 결과를 빠르게 제공하는 정책을 우선한다.
- **검색 유형별 경로:** 초성·태그·제목·별칭은 사전 색인; 선택적 본문은 FTS5; 짧은·흔한 단어·다건은 실측에 따라 기존 A 또는 적합한 경로; 반복 질의는 캐시·연결 재사용을 활용한다.
- **검색 실패는 정상 분기:** “자료 없음”, “색인 누락/검색 미발견”, “자료 있으나 부적합”, “오류”를 구분하되, 검증 때문에 외부 검색보다 느려지는 절차를 만들지 않는다.
- **AI 비용 절약:** 전체 10,000파일을 AI에게 읽히지 않는다. 로컬에서 소수 후보를 선정하고 관련 발췌만 전달한다. 부족하면 필요한 범위만 단계적으로 확장한다.

## 4. 보호·원본 변경의 최소 경계

- 비밀번호, 개인·서비스 계정 인증키, OAuth/접속 토큰, 복구키 등 **실제 인증 비밀**은 강하게 차단하고 일반 검색·AI 전달에 노출하지 않는다.
- 실제 고객 개인정보·실거래 원본처럼 별도 보호가 필요한 데이터가 나타나면 일반 기술자산과 구분하고 필요한 최소 범위로 처리한다. 일반 기술 코드·기술 문서 전체를 막는 이유로 확대하지 않는다.
- 기술자산 원본, 운영 Firebase/Firestore, 운영 검색 DB·서비스, 기존 동결 B/C 산출물, 공식 레지스트리는 명시 승인 없이 변경하지 않는다. **검색·열람의 자유와 원본 쓰기 권한의 제한은 서로 다르다.**
- 위 보호는 등록·색인 등 적합한 시점에 실행한다. 과도한 OS 격리·전수 감사·중복 검증을 일반 검색의 선행조건으로 만들지 않는다.

## 5. 측정할 성공 지표

- **발견:** 10,000건 가정에서 상위 5~6개 파일의 관련성, Recall@6/관련 파일 누락, 사용자 선택까지 걸린 시간. 5~6개는 목표 후보 수이지 모든 정답의 보증이 아니다.
- **시간:** 검색의 첫 후보 표시 지연 p50/p95, 재사용 연결/첫 연결, 관련 문단 추출, AI 적용까지 걸린 시간.
- **비용:** CPU, 메모리·SSD I/O, 색인 등록/변경 비용, AI에 전달한 입력 토큰 및 사용한 검색 호출 수.
- **활용:** 찾아낸 파일에서 유효한 기술을 복원·병합해 새 작업에 적용하고 검증한 비율. 검색 실패 시 외부 검색 전환까지 걸린 시간.
- **근거:** 실측 PASS/FAIL/NOT_TESTED를 분리한다. 정확한 시간·절감률·완전 검색은 시험 전부터 보장하지 않는다.
