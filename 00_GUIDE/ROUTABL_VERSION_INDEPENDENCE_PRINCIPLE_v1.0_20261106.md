# ROUTABL 기술자산 운영 원칙 VI-01 — 버전별 완전 독립성과 공통 원본 분리

- **제정:** 2026-11-06 KST
- **근거:** 사용자 직접 제시한 고객앱 파란색 v20 / 핑크색 v21, 일반 기사앱 / 시니어 기사앱 비유 및 ChatGPT 아카이브 v0.4 회귀 오류 경험
- **분류:** 개발·배포·기술자산 관리에 공통 적용하는 운영 원칙
- **적용 대상:** ROUTABL 일반 기사앱·시니어 기사앱·고객앱·관제웹·기술자산 검색/열람 GUI 및 앞으로 파생하는 모든 버전
- **범위:** 지금은 원칙의 문서화·등록만 수행한다. 실제 앱과 GUI 운영 코드는 이 정책 등록 작업에서 변경하지 않는다.

## 1. 최상위 원칙

> **"버전은 이전 버전 위에 올라앉아 있는 것이 아니라, 동일한 원본을 바탕으로 독립적으로 존재하는 완성품이어야 한다."**

동일한 원본 데이터에 접근하는 여러 앱 또는 GUI 버전은 **각각 독립적으로 설치·실행·검증·유지·교체·삭제**할 수 있어야 한다. 새 버전의 기능·화면·서식·설정 변경은 과거 버전의 파일이나 동작을 임의로 바꾸어서는 안 된다. 과거 버전의 수정 또는 삭제가 새 버전의 필수 기능에 영향을 주어서도 안 된다.

여기서 '공통 원본'과 '이전 버전의 실행 파일'은 서로 다르다. **공통 데이터를 읽거나 정해진 계약에 따라 쓰는 것은 허용되지만, 이전 앱 버전 폴더를 새 버전의 필수 실행 자원 저장소로 사용하는 것은 금지한다.**

## 2. 사용자 설명에 근거한 사례

### A. 라우터블 고객앱
- 고객앱 v20: 파란색 테마로 계속 제공.
- 고객앱 v21: 특정 고객이 원하는 핑크색 테마로 별도 제공.
- 두 버전은 동일한 Firebase / Firestore 프로젝트를 이용할 수 있지만, v21의 UI 수정이 v20의 색상이나 실행 코드에 영향을 주면 안 된다.
- v20·v21 중 어느 것을 설치·배포·제거하더라도 다른 버전은 영향을 받지 않아야 한다.
- 예외: Firebase 데이터 자체, 서버 API, 보안 규칙 또는 공통 스키마를 바꾸면 **모든 이용 버전에 파급될 수 있다.** 공유 데이터 변경은 별도의 호환성·권한·데이터 손실 검토를 필수로 한다.

### B. 라우터블 일반 기사앱과 시니어 기사앱
- 일반 100%, 시니어 140% 화면 크기 등 각 버전의 UI 차이를 유지.
- 시니어앱의 글자 크기·화면 항목·추천 고객 3개 표시 여부를 변경해도 일반 기사앱 화면이나 공유 Firebase 데이터 구조에 영향을 주면 안 된다.
- 공동 업무 로직을 재사용하더라도 배포되는 각 앱의 필수 실행 파일과 설정은 독립되게 관리하고, 공유 기능·공유 DB의 영향은 별도로 회귀 시험한다.

### C. ChatGPT 기술자산 오프라인 아카이브
- 공통 원본: ChatGPT 공식 내보내기 ZIP 및 그 시점의 원본 JSON/첨부파일, 독립 보관 영역.
- 열람 버전: v0.1·v0.2·v0.3·v0.4·향후 v0.5/v0.6 각각 **완성된 독립 실행 GUI**.
- 개별 배포판은 HTML·CSS·JavaScript·검색 인덱스·필수 표시 데이터·첨부파일을 독립적으로 찾고 표시할 수 있어야 한다.
- 이전 GUI의 상대경로에 걸린 필수 CSS·JS·첨부파일 **심볼릭 링크**는 금지.
- 버전 간 동일 inode를 공유하는 **하드링크**는 한 버전에서 내용이 바뀌면 다른 버전에도 전파되므로 필수 실행 자원 공유에 사용하지 않는다.
- APFS copy-on-write / reflink 복제는 분리된 파일 시스템 객체이므로, 별도 inode와 해시를 검증한 경우 물리 저장 공간을 효율적으로 쓰면서 버전별 변경 격리가 가능하다. 기기·파일 시스템이 다르면 일반 독립 복사로 대체한다.
- GUI 버전은 공식 내보내기 *스냅샷*을 표시하는 것이므로 실시간 ChatGPT 계정 상태와 자동 동기화된다고 주장하지 않는다. 새 내보내기와 사용자가 확인한 후속 이동/복원 이력은 **원본/추가 기록의 출처와 시점을 분리**한다.

## 3. 독립성의 네 가지 축

1. **실행 독립성:** 새 버전의 모든 필수 UI·런타임 리소스가 자기 배포물 또는 버전과 무관하게 안정적으로 관리되는 공통 데이터 원본에만 의존한다. 이전 버전을 종료·제거·접근 차단해도 정상 실행해야 한다.
2. **변경 독립성:** 새 버전 수정이 이전 버전 파일을 변경하지 않고, 이전 버전 수정을 통해 새 버전 파일이 자동 변경되지 않아야 한다. 동일 경로 쓰기/하드링크 공유/버전 간 캐시 충돌에 주의한다.
3. **데이터 경계:** 공유 Firebase·Firestore·API·권한 규칙 등은 독립 버전이 공통으로 접근하는 **공유 원본 계약**이다. 버전 독립성은 공유 데이터의 변경 영향이 없다는 뜻이 아니다. 각 버전별 접근권한·호환성·마이그레이션·복구 시험을 별도로 수행한다.
4. **복원 독립성:** 배포된 버전만으로 그 버전의 필요한 파일·설정·명시된 원본 데이터 접근 경로를 확인할 수 있어야 한다. 과거 버전이 없어도 다른 장비나 분리 환경에서 재설치·열람·복원이 가능한지 검증한다. 보존 성공과 복원 성공은 구분한다.

## 4. 새 버전 출하 전 필수 수용 검사 (VI-GATE)

- **VI-01 파일·경로 완결성:** HTML의 CSS/JS/이미지, Android 리소스·설정 등 **필수** 자원의 실존과 해시·정상 로딩을 검사한다. 이전 버전 디렉터리 참조/깨진 링크가 없어야 한다.
- **VI-02 버전 격리:** 이전 버전 폴더 접근 차단 또는 안전한 분리 환경 시험 후 신규 버전의 모든 핵심 기능을 확인한다. 실제 삭제는 별도 승인 없이는 실행하지 않는다.
- **VI-03 기능·화면 회귀:** 변경 요청을 받은 기능 외에는 기존 동작·메뉴·아이콘·배치·색상·글자 크기·상태·정산 결과가 유지되는지 **기능 검증과 실제 시각적 검사**를 모두 수행한다. 특히 이전 버전과 브라우저 렌더링 결과를 비교한다.
- **VI-04 공유 원본 영향:** Firebase/Firestore·서버 API·공유 데이터·권한/보안 규칙/백업 경로를 변경할 가능성이 있으면 사전에 영향 범위와 데이터 손실 가능성을 보고하고 명시적 승인을 받은 후 변경한다. 읽기·쓰기 동작도 회귀 시험한다.
- **VI-05 백업·복원 시험:** 개별 버전의 실행 패키지·원본 스냅샷·확인 기록의 위치/해시를 기록하고, 실제 복원/열람 가능한지 검사한다. 해시 일치만으로 사람의 GUI 복원 성공을 단정하지 않는다.
- **VI-06 원본 불변성과 롤백:** 기존 안정 버전의 코드·데이터·서식을 요청 없이 덮어쓰지 않는다. 이전 버전과 새 버전의 비교/되돌리기 수단을 확보한다.
- **VI-07 사용자 승인:** 버전 삭제, 원본 이동, 앱 배포, 운영 DB 변경 등 비가역적 조치는 사전에 별도로 승인받는다. 확인하지 않은 항목을 '완료'라고 표시하지 않는다.

## 6. 제정 배경: v0.4의 실제 회귀 사례

- v0.3의 좌우 레이아웃 CSS 파일 `v03-style.css`가 v0.4 파일 복제 목록에서 빠지면서 v0.4의 프로젝트 메뉴가 세로로 길게 늘어남.
- v0.4의 첨부파일 폴더가 처음에는 v0.1의 `assets/`를 가리키는 심볼릭 링크여서 v0.1 삭제 시 첨부 열람 기능이 끊길 위험이 있었음.
- 처음에는 기능 중심 시험 15/15로 통과시켜 **CSS 누락과 시각적 회귀를 발견하지 못함**.
- 이후 v0.4에 독립 CSS 및 1,925개 첨부파일을 APFS 복제해 이전 버전 디렉터리를 브라우저에서 차단한 상태로 13/13 검증 완료.
- **증거:** `60_AUDIT/120_OFFICIAL_CHATGPT_EXPORT_20261105_v01/GUI_V04_MISSING_CSS_AND_INDEPENDENCE_FIX_20261106_v0.1.md`
- 기존 GUI v0.1~v0.3은 **삭제하지 않았으며**, 복원 독립성과 전체 GUI 활용성은 해당 버전을 실제로 사용·검증하며 확인해야 한다.

## 7. 시행·기록 원칙

- 이 문서는 앞으로 새로운 버전/파생판 설계·빌드·배포 시 공통 판단 기준으로 사용한다.
- 수정할 파일과 영향받는 기능을 먼저 밝히고, 요청하지 않은 부분은 변경하지 않는다.
- 새로운 GUI·앱 버전의 검증 보고서에는 `VI-01~VI-07` 결과를 **PASS/FAIL/NOT_TESTED**로 기록한다.
- 본 문서 자체도 버전 관리한다. 수정이 필요하면 이 파일을 조용히 덮어쓰지 않고 `v1.1` 등 새 문서와 기술자산 등록부를 생성한다.
- 실제 소스 변경·파일 삭제·운영 서버 변경은 이 문서 제정 자체가 승인하는 것은 아니다.

**관리용 문구:** 공통 원본은 공유할 수 있지만 버전은 서로 독립된 완성품이어야 한다. 백업은 보존, 복원은 연속성, 버전 관리는 격리와 재현 가능성까지 증명해야 한다.
