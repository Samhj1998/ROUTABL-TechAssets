# ROUTABL 기술자산 최상위 원칙 TI-01 — 3-Tier 중요도·보존·복구 우선순위

- **제정일:** 2026-11-06 (KST)
- **관리 ID:** TI-01 (Tier-based Importance & Recoverability)
- **위상:** VI-01 「버전별 완전 독립성과 공통 원본 분리」보다 상위에서 자산 보존·복구 우선순위를 결정하는 운영 철학
- **적용:** 라우터블 기사용 일반·시니어앱, 고객앱, 관제웹, Firebase/Firestore, 정산·세금계산서·백업, ChatGPT 아카이브, Mac Studio·SSD·NAS와 미래의 개발·데이터 자산
- **제정의 근거:** 사용자가 직접 설명한 2026년 10월 영우·세원 월말 결제 사례와 브라질 출장 3단계 짐 분류 경험. 본 문서는 그 철학을 기술자산 관리에 적용한 운영 설계이며, 실제 매출·회계·백업 복원 성공을 별도 검증한 증빙이 아님.

## 1. 최상위 철학

> **원본은 업무를 복구할 수 있는 최후의 근거이고, 프로그램은 그 원본을 활용하기 위한 수단이다.**
>
> **무엇을 반드시 지켜야 하고 무엇은 잃어도 재생성할 수 있는지, 사고가 발생하기 전에 구분한다.**

사용자 비유: **“청산이 있는데 땔감을 걱정하랴?”**

화면·서식·프로그램이 아무리 완성도가 높아도, 원본 데이터를 해석하고 사용하는 수단이다. 원본이 건전하게 보존되면 프로그램 장애 후에도 재개발·이전 버전 실행·출력물 확인·수작업 등으로 업무를 복구할 수 있다. 반면 원본 거래 기록을 상실하면 화면이 멀쩡해도 고객 청구·대금 회수의 근거와 검증 가능성이 위험해진다.

단, '원본'이라는 이름이 붙은 한 저장소만 믿어서는 안 된다. **복구 가능한 시점별 사본, 원본성 검증, 외부 독립 증빙과 복원 시험**이 함께 있어야 한다. 법적·회계적 증빙은 배차기록 외에도 거래명세서·전자세금계산서·고객 확인 등 별도 자료가 필요할 수 있다.

## 2. 발생 배경 — 실제 업무금액과 데이터 가치

사용자가 설명한 2026년 **10월 영우·세원 월말 결제 대상 공급가액은 3,161,000원**이다. 부가가치세 10%가 전액 적용된다고 가정하면 합계 **3,477,100원**이며, 해당 가정은 실제 청구·세금계산서 금액에 대한 별도 검증이 아니다.

- **사고 A — 월간정산 화면·폰트·일자별 매출 표시를 잃음:** 업무가 불편해지고 수작업 시간이 발생한다. 그러나 Firestore 배차·운송 기록이 보존됐다면 기존 버전 복원, CSV·출력, 수기 합산 등 대체 절차를 통해 정산을 재구성할 가능성이 있다.
- **사고 B — Firebase/Firestore 원본 배차 거래 기록 상실:** 앱 화면은 멀쩡해도 거래별 수행·청구 근거를 바로 재현하기 어렵고 대금 청구·회수에 큰 위험이 발생한다. 백업 및 외부 증빙 대조가 복구의 중심이 된다.
- **핵심 판단:** 데이터의 양, 디자인의 아름다움, 코드의 복잡성보다 **손실 시 업무·금전 피해와 복구 가능성**이 보호 우선순위를 정한다.

## 3. 브라질 출장의 3-Tier 분리 원칙과 기술자산 대응

| 구분 | 사용자 실무 사례 | 라우터블 적용 예시 | 보호·복구 방향 |
|---|---|---|---|
| **1st Tier: 핵심·재취득 곤란·상실 피해 큼** | 여권·카드·신분증·지갑 등 | 배차·거래 원본, 고객·거래 관계, 청구·정산 근거, 독립 증빙, 복구 인증수단 | 최우선 보존, 접근 통제, 변경 추적, 독립 다중 백업, 시점별 보관 및 실제 복원 검증 |
| **2nd Tier: 업무 지속 도구·복구 비용 큼** | 노트북 및 즉시 필요한 업무용품 | 정상 앱 APK·소스코드·버전별 UI·업무 로직, 개발환경, 재현 가능한 설정·기술 문서 | 안정판 버전 격리, 빌드·배포 재현성, 복구 시간 최소화, 대체 수단 확보 |
| **3rd Tier: 쉽게 재구입·재생성 가능** | 갈아입을 옷·음식·캐리어의 일반 소모품 | 빌드 캐시·재생성 가능한 임시파일·미리보기·장식용 자료 | 필요한 정도로만 보존, 재생성 절차 유지, 1st Tier 보호 비용을 희생하지 않음 |

**분류는 확장자·파일명·용량·폴더별 영구 고정이 아니다.** 해당 자산이 업무에서 맡는 역할, 독점적 증거성, 의존 관계, 재취득 시간·비용에 따라 달라진다. 예컨대 일반 스크린샷은 3rd Tier일 수 있지만 고객과의 거래 분쟁을 입증하는 유일한 사진은 1st Tier가 될 수 있다. 소스코드도 대체 불가능한 단독 원본이라면 1st Tier로 상향할 수 있다.

**보안 민감도 P0~P3와 업무 복구 중요도 1st~3rd는 별개 축이다.** 개인·고객정보, 비밀번호, Admin SDK JSON·복구키는 중요도와 무관하게 노출하지 않고 기존 접근·암호화 정책을 따른다.

## 4. 데이터와 표시·도구의 분리

1. **원본 계층:** Firestore의 실제 배차/거래 데이터, 고객 정보, 증빙, 공식 ChatGPT 내보내기·원문·프로젝트 ID, 필요한 승인·변경 이력.
2. **복원 계층:** Google Drive·NAS·암호화 백업·시점별 사본과 무결성 기록, 백업을 실제 읽을 수 있는 복구 절차.
3. **활용 계층:** Android 일반·시니어·고객앱, 월간정산 GUI, 기술자산 검색 앱·ChatGPT 아카이브 v0.x, CSV·리포트·세금계산서 생성 도구.

이 계층은 3-Tier 중요도와 같은 분류는 아니다. 하나의 원본이 여러 위치에 복제되고 여러 도구에서 열람될 수 있으므로, 자산 **역할(원본·사본·도구)**과 **복구 우선순위(1st~3rd)**를 각각 기록한다.

## 5. 보호와 복구의 순서

- **예방:** 1st Tier의 삭제·대량 변경·마이그레이션·권한 수정은 위험 평가 및 명시 승인 후 시행한다. 개발·UI 수정은 기본적으로 원본 데이터에 영향을 주지 않아야 한다.
- **다중 보존:** Firestore만 신뢰하지 않고 Google Drive·NAS·필요시 Time Machine 등의 서로 다른 실패 영역에서 백업 상태를 확인한다. 백업 저장 위치와 동작 경계는 검증된 실제 구성에 따라 기록한다.
- **시점 분리:** 오류나 삭제가 자동 동기화되어 모든 백업으로 전파되지 않도록, 정상 시점의 불변/버전별 백업과 보관 기간을 검토한다. 백업 성공 로그와 복구 성공은 구분한다.
- **실제 복원:** 별도 환경에서 JSON/CSV 열람, 고객·일자·배차·금액 건수 대조, 손상·누락 확인, 필요시 업무 정산 재구성까지 검증한다. 운영 Firestore를 시험 복원으로 덮어쓰지 않는다.
- **대체 업무:** 월간정산 GUI가 고장 나더라도 출력·CSV·수기 계산 등 최소한의 대금 청구 절차를 확보한다.
- **복구 우선순위:** 1st Tier 증거·데이터 복구 → 2nd Tier 실행 도구·환경 복구 → 3rd Tier 재생성 가능 요소 정리. 단, 생명·신체 안전·계정 침해 차단 등 긴급 위험은 이 우선순위보다 먼저 대응한다.
- **검증되지 않은 상태:** 실제 사용량·청구액·백업 성패·RPO/RTO 목표는 임의 수치로 확정하지 않는다.

## 6. 기술자산 등록부에 추가할 분류 기준

자산마다 필요한 경우 다음 항목을 추가 기록한다.

| 항목 | 의미 |
|---|---|
| `importance_tier` | FIRST / SECOND / THIRD / UNASSESSED |
| `business_role` | ORIGINAL / EVIDENCE / BACKUP / APPLICATION / DERIVED / REGENERABLE 등 |
| `loss_impact` | 손실 시 실제 업무·금전·증빙·연속성 피해 |
| `recovery_source` | 어느 원본·백업·외부 증빙에서 복구할 수 있는가 |
| `restore_procedure` | 단계별 복구 방법과 데이터 덮어쓰기 방지 |
| `recovery_validation` | 실제 검증된 복원 시험과 일자/근거, 또는 NOT_TESTED |
| `dependencies` | 원본·백업·버전·권한 등 단일 장애점 |
| `approved_retention` | 시점별 보관·삭제 승인 상태 |

이 필드를 전 자산에 근거 없이 자동 할당하지 않는다. 특히 오래된 레지스트리의 모든 항목을 일괄 1st/2nd/3rd로 판정하지 말고 검증 후 분류한다.

## 7. 버전 독립성 원칙 VI-01과의 관계

- **TI-01 (상위): 무엇이 가장 중요하며 무엇을 먼저 지키고 복원할 것인가?**
- **VI-01 (하위 실행 원칙): 공통 원본을 안전하게 공유하면서 각각의 앱·GUI 버전이 어떻게 독립 실행·교체·삭제될 것인가?**
- 두 원칙은 함께 적용한다. 앱 버전의 독립성이 확보되어도 Firestore 원본 손실 위험이 해결되는 것은 아니며, 반대로 원본 백업이 있어도 GUI·앱 복구가 필요 없어진 것은 아니다.
- 이전 버전의 실행 자원 의존을 없애는 작업은 2nd Tier의 복구 역량을 높이는 조치이고, 원본·증빙·복원 시점을 지키는 작업은 1st Tier의 보호 조치이다.

## 8. 실제 사례 보존과 시행 경계

- 출처: **사용자 자신의 2026-11-06 사례 설명** 및 이에 대한 개발 원칙 검토.
- 금융 금액은 사용자가 설명한 업무 상황을 문서화한 것이며 실제 Firestore 매출 합계·부가세 발행 내역 확인 결과가 아니다.
- 맥스튜디오 기존 NAS·Google Drive·Time Machine 백업이 있다는 설명 자체를 **전체 데이터 복원 완료**의 증거로 취급하지 않는다.
- 본 문서의 등록은 데이터 백업·복구 작업 실행이나 Firestore 앱 코드 변경을 뜻하지 않는다. 해당 작업은 별도 범위 확인·승인·검증이 필요하다.
- 원칙 수정 시 원본 v1.0을 덮어쓰지 않고 v1.1 등을 별도로 작성해 기술자산 등록부와 계보를 갱신한다.

**최종 판단 문구:** **“백업은 데이터의 생존을 확인하는 것이고, 복원은 업무의 연속성을 증명하는 것이다.”** 이 문구는 2026-11-06 대화에서 정리된 원칙 표현이며 과거 동일 문구의 발언 시점을 별도로 증명하는 인용이 아니다.
